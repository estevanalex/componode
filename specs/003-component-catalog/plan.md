# Implementation Plan: 003-component-catalog

**Branch**: `003-component-catalog` | **Date**: 2026-09-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/003-component-catalog/spec.md`

## Summary

Deliver a searchable, filterable component catalog dashboard, a component detail view, first-class `ComponentGroup` management, and the remaining v1 importers (AWS, Azure, Kubernetes, Web URL, API URL, MCP server) on top of the `002` importer framework.

## Technical Context

- **Language/Version**: TypeScript 5, Node.js LTS
- **Primary Dependencies**: Fastify, Kysely, React 18, TanStack Query, Vite, Tailwind CSS v4, shadcn/ui
- **Storage**: PostgreSQL (B-tree indexes on `components.name`, `components.slug`, `components.externalId`, `components.componentGroupId`)
- **Testing**: Vitest (unit + integration with `@testcontainers/postgresql`), React Testing Library
- **Target Platform**: Single-instance Docker Compose (backend serves frontend static)
- **Performance Goals**: Catalog list loads in under 1s for 1,000 components; pagination at 50 items per page
- **Constraints**: No `sql.raw()`; all DB access via Kysely; in-process importers; `Component` belongs to at most one `ComponentGroup`
- **Scale/Scope**: Up to 1,000 components in default catalog view; six new importers

## 1. Objective & Acceptance Criteria

### Objective

Implement the component catalog and remaining importers so that:
- any authenticated user can browse, search, and filter components;
- any authenticated user can view component detail with instances and group;
- editors and admins can create and manage `ComponentGroup` records and assign components;
- the six new v1 importers yield `DiscoveredAsset` records and pass tests.

### Acceptance Criteria

- [ ] `GET /api/v1/components` supports pagination, filtering, and search per the spec.
- [ ] `GET /api/v1/components/:id` returns component detail with instances and group.
- [ ] `GET /api/v1/component-groups` lists groups; `POST`/`PATCH`/`DELETE` are admin/editor only.
- [ ] `PATCH /api/v1/components/:id` allows setting `componentGroupId`.
- [ ] The AWS, Azure, Kubernetes, Web URL, API URL, and MCP server importers are configured and tested.
- [ ] Frontend `/components` page, component detail page, and group management page render and work.
- [ ] `pnpm test:unit` and `pnpm test:integration` pass for `core`, `backend`, all importers, and `frontend`.

## 2. Scope

### In scope

- DB migration adding `componentGroupId` to `components` and the new `component_groups` table.
- Backend services and routes for catalog listing, detail, and `ComponentGroup` CRUD.
- Frontend catalog, detail, and group management UI.
- Six new importer packages: AWS, Azure, Kubernetes, Web URL, API URL, MCP server.
- Metrics for component count and group count.

### Out of scope

- Product hierarchy (`DigitalProduct`, `COMPOSES`, `CONSUMES_FROM`) — 004.
- Component-to-component edges (`DEPENDS_ON`, `SOURCES_FROM`, `EXPOSES`) — v2.
- External secret stores beyond `env:VAR_NAME`.
- Webhook/event-driven triggers.
- E2E tests.

## 3. Detailed Implementation

### Phase A — Core and schema

1. Update `packages/core/src/contracts/component.ts` to add `componentGroupId?: string | null`.
2. Create `packages/core/src/contracts/component-group.ts` with `ComponentGroup` fields.
3. Create `packages/core/src/schemas/components.ts` for list filters and group CRUD.
4. Create `packages/backend/src/db/migrations/005_component_catalog.ts`:
   - `component_groups` table.
   - `components.componentGroupId` FK nullable.
   - B-tree indexes on `components.name`, `components.slug`, `components.externalId`, `components.componentGroupId`.
5. Update `packages/backend/src/db/types.ts`.

### Phase B — Catalog backend

6. Implement `packages/backend/src/services/component-catalog-service.ts` with:
   - `listComponents({ page, pageSize, filters, search, sort })`
   - `getComponentById(id)`
7. Implement `packages/backend/src/services/component-group-service.ts` with CRUD and slug enforcement.
8. Implement `packages/backend/src/routes/components.ts` and `packages/backend/src/routes/component-groups.ts`.
9. Add RBAC actions: `component:read`, `component:update`, `componentGroup:create`, `componentGroup:update`, `componentGroup:delete`.
10. Add `metrics.ts` counters for `components_total` and `component_groups_total`.

### Phase C — Catalog frontend

11. Add `packages/frontend/src/api/hooks/components.ts` for list, detail, filters, and groups.
12. Implement `packages/frontend/src/pages/components.tsx` with table, filters, search, and pagination.
13. Implement `packages/frontend/src/pages/component-detail.tsx` with instances and group info.
14. Implement `packages/frontend/src/pages/component-groups.tsx` for group CRUD and assignment.
15. Add route wiring in `packages/frontend/src/routes.tsx`.

### Phase D — New importers

16. For each `packages/importer-<provider>/`:
    - `package.json`, `tsconfig.json`, manifest, config schema, `importer.ts`, unit tests.
    - Yield `DiscoveredAsset` with `category` from the 24-value taxonomy and `provider` matching the package.
    - Validate each yielded `DiscoveredAsset` with `validateDiscoveredAsset` from `@componode/core`.
    - Use the SDK or fetch appropriate for the provider:
      - AWS: `@aws-sdk/client-*` or REST.
      - Azure: `@azure/arm-*` or REST.
      - Kubernetes: `@kubernetes/client-node`.
      - Web URL: `fetch` with health/title probes.
      - API URL: `fetch` with OpenAPI/health endpoints.
      - MCP server: MCP client. Config requires `resourceTypes: string[]` and an optional `endpoint: string`.
17. Add backend registry entries and `pnpm-lock` updates.
18. Add integration tests for each new importer using mocked SDKs/fetches.

## 4. Constraints

- TypeScript 5, Fastify, Kysely, React 18, Tailwind v4, shadcn/ui.
- All DB access via Kysely builder; no `sql.raw()`.
- Importers depend only on `@componode/core`.
- `Component` belongs to at most one `ComponentGroup`.
- In-process scheduling from 002; no new scheduling logic.
